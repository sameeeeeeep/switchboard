The Switchboard User Journey A narrative companion to the PRD. It walks every journey end to end — states, edge cases, and the honest boundary between what ships today and what is still a drawing — as prose and tables, not a canvas.

Switchboard runs your own Claude across every app you use. A stranger installs two halves (a Chrome extension and a notarized Mac app), signs into a third thing (Claude Code), pairs a fourth (this browser to the local daemon), then approves a scope — before anything happens. Every one of those is a place to lose them. This document is the map of that path and everything hanging off it.

How to read the status marks
Every screen and state carries an honest mark. This document trusts the code over the docs, and keeps the marks the audit assigned.
shipped in main / live — code exists and is exercised partial real code with a named gap — the honest majority mock renders but doesn't persist or isn't in the shipped surface aspirational designed in docs, not built
The one invariant, restated
The engine drafts and decides. A human gates every irreversible act. Connectors act, not the engine. The per-action consent gate — exact-match, fail-closed — is the moat, and it is the same gate whether the caller is a wrapp, God, or Autopilot.
00

The spine — one setup ladder

Every readiness question the product can ask is one rung of a single, strictly-ordered ladder in packages/protocol/src/health.ts. Rung N is meaningless until N−1 holds. The ladder is rendered the same way everywhere — the connect chip on the page, the widget, and the menu-bar panel all read HealthStatus.stage and never re-derive it. Surfacing the first unmet rung only is what stops four simultaneous nags.

Two lanes hang off the side of the ladder because they are opt-in and their absence is not a failure: team (off / off-ladder / hosting / joined) and cloud (off / keyed / entitled). They must never block or decorate rungs 0–7.

The rules about when to speak

The failure mode is not "no guidance" — it is guidance that fires on arrival, four times at once, or nags about rung 6 while rung 1 is unmet. Five rules hold everywhere:

Quieting rules (docs/STATES.md §3)
  • One rung at a time. Render stage, never a checklist. The ordinal guarantees it.
  • At the moment of intent, not on arrival. A first-timer gets the page, not a wall; guidance appears when they press the thing that needs the missing piece.
  • Never a dead end. Every state has exactly one primary action and it is never disabled — "the button is NEVER dead" (sidepanel.ts).
  • Sticky bits beat probes for negative claims. Never render "you don't have X" — render "we haven't seen X on this machine." True, reversible, degrades correctly when a probe is slow.
  • Calm words. on / pair to finish setup / sidekick asleep / not set up. Amber for asleep; red only for a genuine mismatch (a rejected token).

Nine journeys, end to end

Each journey below gives the happy path as numbered steps, the screens involved (named, one line each), and the decision points — then the states, edges, and audit follow as reference tables.

01

Discover & install

A two-part install (Chrome extension + notarized Mac DMG) then pairing the browser to the local daemon. This is the longest, leakiest stretch of the funnel — and the copy-paste token is its sharpest friction point.

Happy path

  1. Visitor lands on the marketing page, reads "run your own Claude across every app," and presses Get Switchboard.
  2. They install step A — the Chrome extension from the Web Store (window.claude now injects on allowlisted origins).
  3. They install step B — the Mac app: drag Switchboard.dmg (~207 MB) into /Applications. The installer refuses to plant the LaunchAgent anywhere else (a Gatekeeper-translocation defense).
  4. First launch: the menu-bar app comes up running and shows a pairing token (e.g. A1B2-C3D4), stored 0600 in ~/.relay.
  5. In the extension side panel the user follows the 3-step card: find the menu-bar mark → copy the token → paste & Pair.
  6. Paired. They are on rung 3 — but still one short: Claude Code sign-in (rung 4) surfaces later, not here.

Screens involved

  • Landing page marketing · separate repo"Run your own Claude…" hero, single download button, macOS-13+/Apple-Silicon fine print. partial — lives in the the-last-prompt deploy repo; docs/index.html is a redirect.
  • Two-part install flowStep A "Add to Chrome" + step B "drag to /Applications." shipped — signed + notarized since 0.1.3; first launch just works.
  • First launch + pairing menubar + side panelMenu-bar shows status + token button; side panel shows the 3-step paste card. shipped.

Decision points

Gates in this journey
  • Arch check (missing). The button ships one arm64 DMG to everyone — no OS/arch detection exists repo-wide. An Intel-Mac or Windows visitor gets a dead download. aspirational
  • Paired? On success → onboarding. Token mismatch → the panel goes red and the button re-arms for a re-paste (the one justified red state). shipped
Honest boundary
The tokenless "dial" (hello → approve → mint) is specced in PAIRING.md but not built. Copy-paste-token is the real friction of the whole funnel.
02

First-run onboarding

A menu-bar popover, a readiness ladder that shows only the first unmet rung, and a teach-by-doing strip that carries a stranger to their first connected wrapp. A file marker at ~/.relay/onboarded stops it replaying.

Happy path

  1. Right after install, a first-run popover appears once: "Let's get you running." The user presses Start setup (or Skip).
  2. The setup ladder renders the first unmet rung — daemon ✓, signed-in ✓, then "Senses (screen · mic) — now." They grant senses.
  3. The teach-by-doing strip teaches three gestures by doing them: ⌃⌃ launcher, ⚙ settings, ⌃⌥ summon God. It auto-advances per gesture.
  4. They pick a first wrapp (ideabrain / flow / redline) and press Open & connect — which hands them straight into the core loop.
  5. ~/.relay/onboarded is written; the tour won't replay. "Replay the welcome tour" in Settings re-arms it.

Screens involved

  • First-run popover menubar · onceWelcome + Start setup / Skip. shipped (0.2.8); ~/.relay/onboarded prevents replays.
  • Setup ladder first unmet rungOne ordinal, three consumers; surfaces only the first unmet rung, never re-derives. shipped.
  • Teach-by-doing strip practiceLearn the three gestures by performing them. shipped — auto-advances (unverified on a signed build); house fonts not yet dropped (system-font fallback).

Decision points

Gates in this journey
  • Skip vs Start. Skip leaves the ladder resolvable later from any surface; nothing dead-ends.
  • Connect a first wrapp. The choice of first "aha" wrapp hands the user into Journey 03. shipped
Open question
The 8-rung ladder itself is partial: signed-out (4, red menubar glyph) and unmet (6, needs resolver) are the two soft rungs. signedIn is a sticky verdict + ~/.claude.json marker, not models.length.
03

Use a wrapp — the core loop

The heart of the product: open a wrapp → connect chip → per-origin consent → single input → options + one recommended → per-action gate on every write. This is where the consent grammar is taught and where the moat lives.

Happy path

  1. The user opens a wrapp (say ideabrain). Its header mounts the connect chip — the one affordance every wrapp carries, the MetaMask-account button of Switchboard, rendered in a shadow root so host CSS can't restyle it.
  2. The chip reads its way up the ladder and settles on Connect Switchboard. The user clicks it.
  3. The connect-consent card appears: the models, tools, budget and context the wrapp is asking for, plus a why. The needs resolver checks what the grant is missing. The user presses Allow — the grant is created, never wider than requested.
  4. The chip flips to the identity pill ("Hi Sameep · StayOften"). The user types one line into the wrapp's single input and presses the primary action.
  5. Streaming deltas render. A write-class call (e.g. __generate_image) trips the per-action consent card — the moat. The user Allows this one action.
  6. Results land: ideabrain returns a single verdict card; redline returns A/B/C options with one ⭐recommended, and "Lock" writes the real file.
  7. Grants, budgets, trust-mode and revoke all live in the side panel — the chip carries identity only. Context lending rides in from the menu-bar panel's context selector.

Screens involved

  • Connect chip shadow root · 6 statesIdentity-only header affordance; State = booting | not-installed | unreachable | unpaired | disconnected | connected. shipped — rungFromError covers old extensions.
  • Connect-consent card rung 5aModels · Tools · Budget · Context, each a row, with a why. partial — native card is binary Allow/Deny; silently drops unavailable models (→ SCOPE_EXCEEDED) and renders tools for connectors you may not have (→ unknown_tool).
  • Per-action consent rung 5b · the moat"Allow this action?" — call name, args, class, token cost. shipped — exact-match, fail-closed; Deny is default-safe; classifier defaults to WRITE; 120s timeout fails closed.
  • Representative wrapp ideabrain / redlineSingle input → streamed result. ideabrain = one verdict card; redline = options + one starred pick → Lock writes a real file. Disconnected shows a dashed sample block. shipped.
  • Needs resolver rung 6Met / substitute? / unknown, per connector class. partial — substitution offer designed; claude.ai connectors are unenumerable → inherited:"unknown"; today the gap surfaces at invoke as unknown_tool.

Decision points

Gates in this journey
  • Allow / Deny at connect. Grant created only on Allow, scoped to the request.
  • Grant mode governs every write: ask (default → surfaces the per-action card) · trust (auto-allow within grant) · readonly (refuses writes). Set in the side panel / daemon setMode, not on the chip.
  • Needs met / substitute / blocked. A missing optional need degrades to a quieter app; only a missing required need blocks, and it blocks with a remedy.
The house atom
One input → options + one starred pick is the pattern the wrapp doctrine converges on. ideabrain returns a verdict; redline returns options — both drafts, both gated on write.
04

The menu-bar panel

The black window that drops from the notch — connected apps, the model cloud (cloud + local), tools, context, settings, and the daemon controls. It's the OS surface: the always-there home for everything the chip deliberately doesn't carry.

Happy path

  1. The user clicks the menu-bar mark; the panel drops from the notch (620pt) in its expanded state.
  2. Left rail: a DotMatrix status ("Working — flow · transcription 3s"), the context selector ("No context" by default), and daemon controls (logs · restart · ⚙ · power).
  3. Right pane: connected apps (favicon tiles + a store button), the command centre model list (Opus / Sonnet / Haiku + local llama), and the tools list.
  4. They flip ⚙ to Settings — nine accordion rows — or press ⌥⌥ to open the notch launcher.
  5. A stale-daemon banner ("Update ready — restart") appears when the bundle mtime outruns the running pid; Restart resolves it.

Screens involved

  • Menu-bar panel expanded · 620ptLeft status/context/daemon column + right apps/models/tools rails. partial — only the expanded state is built; the closed grey-dot pill + hover-peek is the next task. Team is NOT mounted here.
  • Settings accordion · 9 rowsName · God's voice · Mode · Models · Shortcuts · What God sees · Connections + Replay tour. shipped — ≤1 open at a time; "Economy" writes ~/.relay/economy, a model deny-list (opus→sonnet→haiku), never a silent hosted/local swap.
  • Notch launcher ⌥⌥ · HOME / SPOTLIGHTJump-back-in + recent, or typed query → grouped results; a file-drop bar makes it file-first. shipped.
  • Context selector running onlyLends a project (a Bank vault) into every wrapp's grant as the Context row; default "No context." shipped.

Decision points

Gates in this journey
  • Which context to lend. Default is none; the lent project rides into consent, so it is an explicit privacy opt-in.
  • Economy mode. A post-gate model downgrade — no extra grant needed, and it can't do tools locally, so tool calls stay on the hosted route.
  • Stale daemon → Restart. The detector is real; the version train (Info.plist / manifest / tag) drifts, so the number a user reads isn't yet trustworthy. partial
05

The store

Two real tiers over ~/.relay/catalog.json (~76 entries): a featured front and a classic rail/detail. "Add local" is real; GitHub import and live skins are drawings.

Happy path

  1. From the panel's STORE button, the user lands on the featured front (Tier 1): category chips (All / Apps / Skills) with real counts, "apps we love right now," and the honest pitch "Free · runs on your Claude."
  2. They browse into the classic view (Tier 2): a category rail + a detail pane showing what a wrapp is "made of" (skills · workflows · UI) and what it "needs."
  3. They install via one of three doors: Get (from the catalog), Add local (a folder picker that validates switchboard.json), or GitHub import (a gap).
  4. Install hands them into the core loop (Journey 03) via the connect chip.

Screens involved

  • Store — featured Tier 1App-Store-style front, real category counts. shipped — Add local is a real folder picker validating switchboard.json.
  • Store — classic Tier 2 · rail + detailBacked by catalog.json + bundled fallback; icons from Resources/icons/<id>.png. shipped — the NEEDS resolver is honestly read-only (fill-drawer is Phase 2).
  • GitHub import (+Create) paste an OSS linkAI assesses port-readiness → add as a wrapp. aspirational — port-assess and Spotify-style rev-share monetisation both unbuilt.
  • Skins live renderersOne catalog, N live-switchable layout renderers + DESIGN.md tokens. mock — 4-skin demo artifact, not wired into the shipped store.

Decision points

Gates in this journey
  • How to add: Get (catalog) · Add local (folder) — both real — vs GitHub import (gap).
  • "Resolve 2 & Run". Honest-read only today — connector/native reqs aren't yet observable, so the button promises more than the fill-drawer can keep. partial
06

The notch / Presence (Guru)

One card grammar — ask · guide · notify — that descends from the notch, is clickable there, carries provenance (thread · project), and returns an answer as JSON. The founder works away from the terminal; presence is how any thread reaches them.

Happy path

  1. A Claude Code thread (say migrate-db) needs a decision. It raises a presence card that descends from the notch, headed with its provenance (◆ StayOften).
  2. The card shows the question and options: ⌥1 Ship ⭐ · ⌥2 Hold · ⌥3 Ask me later. It's clickable at the notch (bounded hit-rect; the rest stays click-through); dock/cursor placements use the ⌥-keys.
  3. The human answers. The answer returns as JSON and appends to guide-history.jsonl.
  4. A guide card instead runs a walkthrough — a ring points at the target; if a sense is missing it degrades to "do it yourself, then ⌥→." A notify card carries an action row.

Screens involved

  • Presence card notch · clickableProvenance header + question + option row; answer returns as JSON. shipped — the full window.claude.ask verb + queue polish is deferred.
  • Card shapes ask / guide / notifyOne card, three shapes; provenance on all. shipped.
  • Guide lifecycle arming → summaryarming → waiting → sensing → advancing → summary → aborted; never dead-ends; single on-screen cursor enforced. shipped.

Decision points

Gates in this journey
  • Urgency. ambient (auto-dismiss, no sound) · normal (waits, single chime) · blocking (stays until answered).
  • Queue. One card on screen at a time; the pill shows +1 when queued.
  • Caller gone. Resolves locally but is still written — the answer isn't lost even if the asker left. shipped
07

God

⌃⌥ summons an ambient assistant that sees (screencap + vision), speaks (native MLX TTS), points ([POINT:x,y]), and acts via gated, audited hands — the same gate as every wrapp.

Happy path

  1. The user holds ⌃⌥. The glow cursor arms → listening (live transcript). God sees the screen via screencap + vision (it auto-treats on-screen text as untrusted).
  2. God answers by speaking, and can point with [POINT:x,y] or open a draggable canvas (Save / Copy).
  3. To act, God's hands (open / type / click / key + [RUN] a wrapp) run inside a floating WKWebView with an injected window.claude shim.
  4. Any write trips "Allow this action?" — the same fail-closed, audited gate every wrapp uses (trust-mode grant + per-action notch gate).
  5. The menu-bar dot maps to health: lime idle · slate offline · red signed-out.

Screens involved

  • God — notch states ⌃⌥ holddot idle → working (breathing) → listening (transcript) → canvas → consent. shipped — persona is swappable JSON; can load offscreen so the notch drop is the surface.
  • God cursor + health glow statesFull-screen, click-through cursor; health colour maps to the dot. shipped.
  • Allow this action? same gateGod's hands ride each wrapp's own gate + audit, not a new one. shipped.
  • Permission grants AX · Screen · MicTCC grants; Accessibility is drag-in. shipped — signing-identity changes churn TCC grant persistence.

Decision points

Gates in this journey
  • Senses granted? Missing AX/Screen/Mic → onboarding re-requests; God never silently fails.
  • Every hand is a gated action. Reversible → trust-mode auto within grant; irreversible → the per-action card.
  • Hands = reused wrapp actions. God grows by [RUN]-ing existing actions via the switchboard connector, not by rebuilding them. partial — God is per-hotkey, not self-running; the observe→act loop and AX-tree targeting are still ahead.
08

Autopilot / Company-OS

A portfolio of companies, each drilling into a command centre read as an autonomy gradient: Made · Waiting · Your call. Every move is sorted by one question — can this be undone? Reversible moves run while you sleep; irreversible ones wait at a gate for one tap; strategic ones surface as decisions only you can make.

Happy path

  1. The founder locks a company's 4 decisions (Offer · Who · Edge · Model — draft is the machine's, lock is yours). The daily loop reads Identity and drafts 3–5 highest-leverage moves.
  2. The portfolio shows every company advancing at once: "made 3 · waiting 2 · calls 1."
  3. Drilling into a command centre, the reading order is the gradient: Made (reversible, done — a draft filed in Bank) → Waiting (gated, one tap) → Your call (founder decision).
  4. For a Waiting move, God prepares the exact content as a reversible preview. The founder reviews the real thing and presses Approve & send — which calls relay__autopilot_dispatch through a connected sender and the daemon's gate.
  5. If no sender is connected for that channel, the button is honestly Connect to send; the move stays staged. Zero unattended sends, ever.

Screens involved

  • Portfolio many companiesPer-company made/waiting/calls counts, reads real portfolio storage. partial — the cockpit runs at sameep.ai, NOT in the manifest allowlist, so in-extension it's only been tested with a mock provider.
  • Command centre drill-in · gradientIdentity above; Made / Waiting / Your call lanes. partial — "Approve & send" calls relay__autopilot_dispatch; routineDispatch/pageDispatch is the one audited outward path.
  • Company-OS states 8 statesfresh · running · awaiting you · paused · out-of-runway · no-connector · failed · no-sender. partial — out-of-runway isn't rendered in cockpit.html (metering lives only in the separate autopilot/index.html).

Decision points

The gradient — who acts
  • Reversible → autopilot / God's hands. Produces a draft or artifact; undoing it is deleting a draft. shipped
  • Irreversible → gate, one tap. Publish / send / deploy / charge. The send line never moves; no autonomy promotes a GATE move.
  • Strategic → founder decision. Hiring, pricing, legal, relationship. God never touches these.
  • Auto-mode toggle (Assisted vs Full auto) is per-company in ~/.relay/autopilot.json — but the cockpit toggle is mock: it mutates local JS only, unreachable from origin storage.
The honest boundary
Full-auto is wired in the routine, but every channel is no-sender today (no publisher/email connector connected) — so nothing sends until one is. The one number always honest is tokens spent; metered exactly, so background work is never invisible.
09

Team Mode & Bank

Team = host / join-with-code, with no login (invite = membership; Pro rides inside the code). Bank = the context vault (contexts.json + .md notes) that feeds every wrapp as lent context. A bound folder is a real vault.

Happy path

  1. A user turns on Team Mode in the side panel and either Hosts a team (an invite code goes live) or Joins with a code.
  2. There is no account and no login: membership is possession of the invite code; the Pro entitlement is a signed string that rides inside the code, so members inherit it without signing up. Seats are enforced by counting live sockets.
  3. Joining adopts the shared folder as the active project.
  4. Separately, the user's Bank holds a bound folder as a vault; its .md notes are lent into every wrapp's grant via the menu-bar context selector.

Screens involved

  • Team mode side panelHost / Join-with-code; no login. partial — daemon team.* (status/host/join/leave/entitlement/git) is wired, but the Mac panel does NOT surface team (TeamSection.swift drafted, unmounted); billing unbuilt.
  • Bank — context vault contexts.json + .mdBound folder = a real vault; feeds every wrapp as lent context. shipped — renders truthful-empty until a vault has notes; the Bank connector (push to-dos from any thread) is next.
  • Team lane states off-ladderoff · hosting · joined · billing. partial — an off-ladder lane that never blocks rungs 0–7; billing (Stripe → entitlement minting) is the missing piece.

Decision points

Gates in this journey
  • Host vs Join. Both work today, free; no page to open, no login to help with.
  • Origin allowlist. window.claude injects only on thelastprompt.ai / *.thelastprompt.ai / localhost. A new origin (e.g. sameep.ai) silently shows "Get Switchboard" until added to BOTH lists + the extension reloaded. aspirational-fix
  • Cloud backup → Pro. The gate exists and refuses correctly; billing is the one honest "not yet."
