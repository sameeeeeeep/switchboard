# LinkedIn launch post

## Primary post

My feed is full of people building with AI.

In everyday conversations, I meet people who are still figuring out what to do with ChatGPT. Claude Code sounds like something for developers. Most of the apps in my feed never reach them.

I keep thinking about the gap between those two worlds.

Someone builds a useful tool. To try it, you need to clone a repo, install dependencies, find an API key, connect your accounts and explain your project again.

The person who just wants to launch a brand has already left.

That’s why I’m building Switchboard.

It connects lightweight apps to the AI you already use, the tools you’ve connected and the project context you choose to share.

So an app can be small and focused, while the experience is personal to you.

Take building a brand.

Claude Code gives you a powerful coding environment. A brand-building app should give you a place to develop a brief, research the market, compare competitors and make decisions about the brand.

The AI can be the same. The experience should fit the job.

Then you open AdForge to make ads. It can work from the brand context you’ve already built, instead of asking you to start the conversation again.

A logo tool, a website reviewer and an ads analyst can each give you a different way to work with that same project.

Switchboard is the connection between them: your AI compute, your tools and your context, available to the apps you allow.

Today, that includes Claude Code and Codex, with local models for supported tasks such as voice and text processing. There’s an initial setup, and individual apps need permission to use it.

For builders, this opens up a different way to distribute software. Build the useful interface and agent behaviour. Connect it to the user’s setup.

For everyone else, the promise is simpler: find an app for what you need to do, open it and get to work.

I want more of the things we’re building with AI to become things people actually use.

That’s the direction I’m taking Switchboard.

What’s one task you wish had its own app, running on your AI?

# Switchboard: four-week publishing plan

## The story to build

Switchboard connects useful interfaces to the AI, tools and project context a person already has. The audience should understand the personal payoff before learning the word “harness.”

Use three recurring perspectives:

1. **The person doing the work:** a founder building a brand, making ads, reviewing a website or dictating a note.
2. **The person building the app:** someone with a useful idea who does not want to rebuild authentication, model access and context collection for every product.
3. **The operator underneath:** Switchboard makes the connections, while the user controls access.

One featured project should carry the main demonstration. Verra is already an app-provided sample in AdPulse; don’t silently relabel Allbirds sample ads as Verra. Use the same real project only when its actual cross-app run has been captured.

## Cadence and reuse

- Three core posts per week is enough to sustain the narrative without repeating the launch pitch.
- A single verified 60-second app run can produce a full demo, two short clips, a still and a builder explanation.
- Keep each post about one job. The launch post can explain the larger thesis; later posts should show it.
- Use screen captions to identify the app, project and model. Put caveats about sample data in the shot or accompanying text, not in tiny unreadable footnotes.
- Reuse the visual language: black, lime, dot-matrix headings, actual app icons. Keep screenshots faithful to the apps.
- Do not post every planned item just to fill the calendar. If a feature is not demonstrable, use a candid development update instead of simulated proof.

## What to measure

Track what helps the product, rather than promising reach.

| Signal | What it tells you | Follow-up |

| Requests for particular apps | Demand for a task, not just for AI | Group by job and interview a few people |
| Developers asking for the contract | Builder story is resonating | Share a working minimal example |
| Repeat app usage | The app is useful beyond the demo | Look at the task completed and return path |

Maintain a simple sheet with date, post, format, views, substantive comments, installation questions, reported issues and use-case requests. Record numbers manually or from approved analytics; do not infer installations from impressions.

## Replies worth preparing

**“Isn’t this just another wrapper?”**
The interface is part of it. The more interesting question is whether the app can use your existing AI and project context, act through the tools you allow, and keep useful state. A thin UI alone doesn’t guarantee that.

**“Do I need another AI subscription?”**
Switchboard connects to supported AI you already have, such as Claude Code or Codex. Your provider’s usage limits and charges still apply. Local models support some tasks.

**“Does everything stay on my machine?”**
Local models process locally. Requests to cloud AI and online tools go to those providers. The point is to make the route and permissions explicit, not to call every task local.

**“Can I build an app for it?”**
Yes. Start with the app integration guide and an existing example. Define what your app needs and let users grant access through Switchboard.

**“Can I use my ChatGPT subscription?”**
The current supported path is through Codex with the account access it supports. It is not a promise that every ChatGPT feature or connector automatically becomes available to every app.

**“Are these generated results real?”**
Identify the specific clip: live generation, an app-provided sample, or a conceptual diagram. Never blur those categories in the answer.

# Follow-up posts

## 1. The interface should fit the job

If you’re building a brand, you probably don’t want to begin with a terminal.

You want somewhere to put the idea. A way to compare competitors. A brief you can revise. Decisions you can keep track of.

The AI underneath might be Claude Code or Codex. That doesn’t mean every experience built on it should look like a coding tool.

That’s one of the ideas behind Switchboard: let different apps provide different ways to work, while connecting to the AI and resources the user already has.

Brandbrain is one example of the kind of experience I mean—a workspace built around the decisions involved in creating a brand.

What job do you do today inside a chat that deserves a better interface?

## 2. The brief shouldn’t disappear when you change apps

The most repetitive part of using AI is often explaining the project.

Who the customer is. What the product does. What the brand sounds like. What we decided last week.

Then you open another app and do it again.

I want the project to be something you can give an app access to, rather than something you have to keep pasting into a new conversation.

Switchboard lets compatible apps work with the project context you allow. AdForge, for example, has a path for using a brand supplied through Switchboard instead of starting from a website URL.

That is the useful connection for me: the ad creator gets a brief, the website reviewer gets the same positioning, and you remain in control of access.

What information are you tired of repeating?

## 3. Builders: bring the useful part

Every small AI app seems to inherit a surprisingly large to-do list.

Connect a model. Store credentials. Add tool access. Collect context. Handle permissions. Then, finally, build the thing the app is for.

With Switchboard, I’m exploring a different starting point.

Build the interface and agent behaviour for a specific job. Connect them to the user’s existing AI, configured tools and allowed project context.

You still have to build a good product. A reliable agent doesn’t appear because a model is reachable.

But the useful app shouldn’t have to become another isolated AI setup.

If you could distribute one small, focused app this way, what would it do?

## 4. A harness is more than a prompt sequence

I’ve been using the word “harness” while building Switchboard, and I want to be precise about it.

A form that runs three prompts is a workflow.

A more capable harness gives an agent tools, context, instructions, persistent state and a way to respond to what actually happens. It can ask for information, inspect a result, make another call and let the user intervene.

Some lightweight apps need a simple workflow. Some jobs need that richer agent environment.

Switchboard is the layer connecting either experience to the user’s AI and resources. It doesn’t turn an ordinary app into an autonomous agent by naming it one.

The work is in making the behaviour useful—and making it clear what the app is doing.

Where do you most need an agent to adapt, rather than follow a fixed sequence?

## 5. The first useful screen matters

I tried to look at our apps through the eyes of someone opening them for the first time.

Before they care about models, MCP or agent frameworks, they have a simpler question:

“What can I do here?”

A product page can explain the architecture perfectly and still fail to answer that.

For Switchboard, I’m moving the explanation closer to the work: a brand brief, an ad concept, a campaign decision, a note dictated into an app.

The connection underneath should make those experiences easier to use. It should not become another subject the user has to study first.

What’s the clearest first screen you’ve seen in an AI app?

## 6. Local AI earns its place through small useful tasks

Not every AI task needs a large cloud model.

Voice transcription, text cleanup and a personal dictionary can make everyday work easier when they’re available in the right place.

That’s why local models belong in the Switchboard story alongside Claude Code and Codex.

An app should be able to use the kind of compute its task supports. Sometimes that means a cloud coding agent. Sometimes it means local speech or a local text model.

They don’t all have identical capabilities, and I don’t want the interface to pretend they do.

I want the useful option to be available without asking the user to rebuild the connection each time.

What would you most like to run locally?

## 7. A dashboard should lead to a decision

The interesting question in an ads tool isn’t always “What is my ROAS?”

It might be: “Which creative should I replace?” Or “Where am I wasting spend?” Or “What should I investigate before increasing the budget?”

AdPulse gives that question a place in the interface, beside the account data.

The attached clip uses its built-in sample account. The numbers are a sample, and I’m showing the product interaction—not claiming these are live customer results.

This is the kind of focused software I want Switchboard to support: an interface shaped around a decision, using the person’s own AI and connected resources.

Which recurring decision needs a better tool in your work?

## 8. Useful software needs a usable route to the user

There are AI projects I want to try that I never get around to setting up.

I don’t think the solution is one enormous app that does everything.

I’d rather see more focused tools that can use the setup a person already has.

That’s the bet behind Switchboard: make compute, tools and context available to apps with the user’s permission, so distributing a useful interface becomes easier.

There’s still work to do on compatibility, onboarding and the quality of individual apps. Those are product problems worth solving.

The outcome I care about is straightforward: someone finds a tool for the job they need to do, and actually gets to use it.

What’s a useful project you bookmarked but never installed?

## Filming notes for founder segments

- Camera at eye level; simple, quiet background; window light from one side.
- Record the whole script once, then record each paragraph separately for clean edits.
- Leave one second before and after each take. A calm delivery will work better than a fast feature list.
- Speak “Claude Code” and “Codex” distinctly. Explain the useful task before saying “harness.”
- Record clean voice. Add music only if licensed and if it does not obscure speech.
- Desktop captures: use a clean browser profile and a clearly identified demo project. Keep private accounts, notifications, tokens and personal data out of frame.

## Editing and export

- Make a landscape master and a vertical adaptation. Reframe around the active interaction; do not shrink a whole desktop screen until its text is unreadable.
- Use a 4:5 or 9:16 composition for short clips when the active panel can remain readable. Keep the full desktop version for product explanations.
- Use H.264 MP4, AAC when audio is present, and a consistent frame rate. These are practical export choices, not claims about a platform’s current maximum limits.
- Captions: maximum two short lines at a time. Use real UI labels for exact names; avoid a sentence explaining every cursor movement.
- Export a clean master and a captioned master. Keep original recordings so the edit can be changed without rerecording.
- Keep app-provided sample labels in frame or state the sample status clearly in the edit. Never label an interface walk-through as live generation.
